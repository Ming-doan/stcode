One binary, three shapes

Daemon first. Everything else follows.

The agent is held by a long-lived daemon speaking JSONL over a socket. The TUI is one client; so is a UI on another machine, and so is your own code. Detach does not kill the agent, and a container is a transport setting, not a rewrite.

stcode

On your machine

The UI, plus a daemon started right here if none is listening. What you run day to day.

stcode --headless

In a container

The daemon alone, over a unix socket or TCP. full-auto is only allowed where the blast radius is contained.

stcode --daemonless

From anywhere

The UI alone, attached to a daemon elsewhere. It never quietly runs the work on your laptop; /connect moves it.

Four bets

Each one is traceable to a measurement.

We are not competing on polish. These are the things other coding agents don't do.

01

MCP tools are code, not tool definitions

Other agents ship MCP schemas in the prompt prefix every turn, forever. stcode writes each tool to .stcode/mcp_servers/<server>/<tool>.py and lets the agent grep and import what it needs from a REPL.

02

A supervisor watches the trajectory

The session log already is the trajectory, so the supervisor is just a reader. Counting heuristics run for free — the same call three times, half the calls failing, no file written in N turns — and only a hit spends a cheap model call.

0 tokens while things go well

03

Agent-to-agent messaging has no protocol

Containers share a volume, so a message is a file. No registry, no routing table, no service discovery, no socket mesh. Messages carry paths, not payloads — so team cost does not grow with N².

1 directory per role

04

Containerization is not a rewrite

The daemon holds the agent; the TUI is one client of it. transport = "tcp" is configuration. And full-auto without an approver refuses to start outside a container — in code, with no override flag.

Team mode

One agent, one role, one container.

A BA, a frontend dev, a backend dev and devops, each a daemon in its own container. They share a /team volume with a bare git repo on it. Each role clones and pushes a branch; devops merges. You dispatch per role — there is no lead agent.

  • An agent is a config file. Mount one .toml — prompt, model, tools — and that container is that role.
  • Attach and steer mid-run. A message you send lands at the next tool boundary, not the next turn.
  • One role, one merge boundary. If two agents need the same file, the roles are split wrong.
/team ├── repo.git # bare repo — no creds, no network ├── inbox/ │ ├── ba/ │ ├── backend-dev/ │ │ └── 01JB8…json # {"from":"ba","refs":["specs/orders.md"]} │ ├── frontend-dev/ │ └── devops/ └── specs/ └── orders.md # the content lives here, not in the message $ docker run -e STCODE_SANDBOX=1 -e STCODE_TEAM=1 \ -v team-volume:/team \ -v ./backend-dev.toml:/config/config.toml:ro \ stcode --headless --mode full-auto

Hard rules

Each exists because breaking it failed once.

01

Tool output is elided, never LLM-summarised. The head says what ran, the tail says how it went, the full value stays reachable.

02

Sub-agents cannot spawn sub-agents. Unbounded recursion with no budget is a fork bomb.

03

Sessions are append-only JSONL. cp session.jsonl is the branching feature.

04

full-auto without an approver runs only in a container. The daemon refuses otherwise.

05

The agent never edits its own harness. A self-refining agent once promoted cheating into a skill.

06

Every LLM call lands in the session as usage. One place for cost, and the trace exports from it.
